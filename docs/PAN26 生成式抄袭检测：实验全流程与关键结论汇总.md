## 一、任务概述与核心挑战

本项目针对 **PAN@CLEF 2026 Task 4: Generative Plagiarism Detection**，构建了一套从源检索（Source Retrieval）到文本对齐（Text Alignment）的端到端检测系统。

**任务定义**：给定一篇可疑文档（suspicious document）和一个大规模源文档语料库（corpus，~60K篇学术论文），
1. **阶段1 — 源检索**：从语料库中检索出可疑文档的真实来源文档；
2. **阶段2 — 文本对齐**：在可疑文档与源文档之间精确定位抄袭段落。

**核心挑战**：大语言模型（LLM）生成的抄袭文本不同于传统的逐字拷贝或近义改写——LLM 可能同时融合、重组、改写自数十个来源文档。可疑文档的不同段落可能来自完全不同的来源。传统"将整篇文档作为单一查询"的检索范式在这种"多源合成"场景下存在根本性局限：**查询信号是多个来源指纹的噪声混合，导致真正的源文档被噪声稀释而无法召回。**

## 二、方法演进全景：从文档级检索到溯源图建模

### 阶段总览

| 阶段 | 方法 | 核心思想 | 关键突破 | R@10 | MRR |
|------|------|---------|---------|------|-----|
| 1 | 标准 BM25 | 全文作为单一查询 | 强基线 | 0.888 | 0.768 |
| 2 | E5 Chunking | 源文档切块 + 语义匹配 | 覆盖语义改写盲区 | 0.983 | 0.836 |
| 3 | **Query Segmentation** | 查询分段 + 独立检索 + 源投票 | **显式溯源图建模** | **0.970** | **0.909** |

### 方法哲学演进

```
阶段1:  文档级检索  →  query ↔ doc 打分（传统 IR 范式）
阶段2:  块级语义匹配 →  chunk ↔ chunk 交互（隐式多源建模）
阶段3:  查询溯源建模 →  query_chunk → source_voting（显式 provenance graph）
```

关键跃迁发生在阶段3——**不再将可疑文档视为整体查询，而是将其显式建模为多源拼接的复合体**，每个段落独立"指认"自己的来源，再通过投票聚合重建完整溯源图。

## 三、阶段1：基线模型（标准 BM25）

### 方案设计

对 60,592 篇源文档构建倒排索引（inverted index），以整篇可疑文档为查询，选取 IDF 最高的 100 个查询词进行 BM25 评分，返回 Top-K 候选。

### 实验数据

**全量训练集（42,444 查询）**

| 指标 | 数值 |
|------|------|
| R@1 | 0.7101 |
| R@10 | 0.9196 |
| R@100 | 0.9769 |
| nDCG@10 | 0.8184 |
| MRR | 0.7856 |

**800 查询样本验证（seed=20260520）**

| 指标 | 标准 BM25 (max_terms=100) |
|------|---------------------------|
| R@10 | 0.9200 |
| R@100 | 0.9700 |
| nDCG@10 | 0.8122 |
| MRR | 0.7771 |

### 核心问题定位

1. **Cat1 盲区（源文档未进 Top100）**：约 982/42444（2.3%）查询的源文档完全无法被标准 BM25 召回
2. **多源信号稀释**：长文本（>20K 字符）查询包含多个来源的内容片段，作为单一查询检索时关键词被稀释
3. **语义改写无覆盖**：BM25 仅能匹配词法重叠，对 LLM 改写/同义词替换类抄袭无效

## 四、阶段2：E5 Chunking 稠密语义补盲

### 方案设计

- 对 BM25 盲区查询（Cat1），将候选源文档切分为 256-token 重叠块
- 使用 E5-base-v2 编码查询与文档块，计算余弦相似度
- Coverage-aware scoring: `0.5 × top1 + 0.3 × top5_mean + 0.2 × coverage`
- 以 Chunk 检索结果替换 BM25 无效排名

### 实验数据

| 指标 | BM25 基线 | BM25 + E5 Chunk | 提升 |
|------|----------|----------------|------|
| R@10 | 0.9196 | **0.9830** | +6.9% |
| R@100 | 0.9769 | **0.9917** | +1.5% |
| nDCG@10 | 0.8184 | **0.8716** | +6.5% |
| MRR | 0.7856 | **0.8355** | +6.4% |
| Cat1 恢复率 | - | **76.7%** | - |

### 关键洞见

1. E5 Chunking 本质是**隐式 Query Decomposition**——块级交互已完成语义层面的多源解耦
2. 任务的核心难点是**语义改写而非词法匹配**
3. 已触达"文档级打分"范式的天花板，剩余盲区为多源重度融合/强改写样本

### 失败的优化尝试

| 尝试 | 方案 | 结果 | 原因 |
|------|------|------|------|
| Coverage-Aware 打分 | 引入 chunk 覆盖度权重 | 无增益 | 同领域论文共享语义流形，无关文档也能匹配大量 chunk |
| RRF 多源融合 | BM25 + E5 Chunk 双路融合 | 仅小幅优化排序 | 两路错误模式高度重叠 |
| Query Chunk IDF 加权 | 提升专业术语权重 | 反向降分 | 加重改写类抄袭匹配难度 |

## 五、阶段3：Query Segmentation — 显式溯源图建模（最终提交方案）

### 范式转变

这是本项目最关键的范式转变。此前所有方法（包括 E5 Chunking）本质上仍是 **query ↔ doc scoring**——无论 block 粒度多细，最终都是计算某种 similarity(doc, query)。但生成式抄袭的本质决定了：

> **多源抄袭应使用多查询检索。** 可疑文档的不同段落来自不同来源 → 每个段落应独立查询自己对应的来源 → 最后通过投票聚合重建溯源图。

### 方案设计

**三步流水线**：

```
可疑文档
  │
  ├─→ 段落分段（paragraph_split）
  │     · 按双换行符拆分段落
  │     · 合并至 3000 chars / 丢弃 <800 chars 残段
  │     · 每个查询上限 20 段
  │
  ├─→ 独立分段检索（Independent Segment Retrieval）
  │     · 每段独立 BM25 检索 Top-50
  │     · max_terms=20, max_df=5000（性能优化）
  │
  └─→ 覆盖率加权源投票（Coverage-Weighted Source Voting）
        Score(d) = Σ BM25(d|cᵢ) × (1 + count(d)/n)
        · count(d)：检索到文档 d 的查询段数量
        · 被多个段同时命中的文档获得额外加分
```

### 关键技术突破：Chunk BM25 性能优化

**问题**：分段 BM25 搜索比标准 BM25 慢 100 倍。每个 3K-char chunk 的搜索耗时 1.7-3.0s（标准全查询仅 0.02s）。

**根因分析**：Chunk 仅含 ~150-250 个 unique tokens，大多数是常见学术词汇（"method", "analysis", "result"等）。这些词的 IDF 极低，posting list 可达 30K-50K 条目。50 个 query terms × 30K posting entries = 150 万次 scoring 操作 —— 相比之下，全查询选中的 50 个 terms 多为罕见词，posting list 通常仅几百条。

**修复方案**：

| 优化 | 说明 | 效果 |
|------|------|------|
| `max_df=5000` | 过滤文档频率 >5000 的 term（~8% 语料） | 消除超长 posting list 遍历 |
| `max_terms=20`（chunk） | chunk 仅使用 20 个 query terms | 减少无效 scoring |
| `heapq.nlargest` | 堆排序替代全排序 | O(N log k) vs O(N log N) |

**修复后**：单 chunk 搜索从 1.7-3.0s 降至 0.15s（**20x 加速**）。

### 实验数据

**800 查询样本（seed=20260520，submit_pan26.py 精确代码验证）**

| 指标 | 标准 BM25 | 分段 BM25（本文方法） | Δ |
|------|----------|-------------------|---|
| **R@10** | 0.9200 | **0.9700** | +5.4% |
| **R@100** | 0.9700 | **0.9912** | +2.2% |
| **nDCG@10** | 0.8122 | **0.9242** | +13.8% |
| **MRR** | 0.7771 | **0.9092** | **+17.0%** |

**1200 查询样本（验证集，seg_compare.py 验证）**

| 指标 | 标准 BM25 | 分段 BM25（本文方法） | Δ |
|------|----------|-------------------|---|
| **R@10** | 0.8825 | **0.9692** | +9.8% |
| **R@100** | 0.9517 | **0.9908** | +4.1% |
| **nDCG@10** | 0.7850 | **0.9234** | +17.6% |
| **MRR** | 0.7532 | **0.9086** | **+20.6%** |

### 关键洞见

1. **MRR 提升最大（+17%~+21%）**：覆盖率加权投票能有效地将真实源文档从低排名"推"到前列。标准 BM25 可能将源文档排在 5-10 名，分段投票通过多段一致性信号将其提升至 1-3 名。

2. **分段方法对查询分布更鲁棒**：800q 样本的标准 BM25 R@10 为 0.920，1200q 降至 0.883（-4.0%）；而分段方法的 R@10 在两个样本上几乎一致（0.970 vs 0.969），波动仅 0.1%。

3. **R@100 接近理论上限（0.99）**：源检索召回率已接近饱和，剩余错误应在文本对齐阶段处理。

4. **99.8% 的查询被分段**：绝大多数可疑文档具有多段落结构，说明多源合成是数据集的普遍特征而非边缘情况。

5. **纯 BM25 架构，无 GPU 依赖**：分段方法仅需 numpy + Python 标准库，Docker 镜像 < 200MB，已在 TIRA 成功提交（team: fosuai, software: oscillating-list）。

### 与 E5 Chunking 方案的定位差异

| 维度 | Query Segmentation（阶段3） | E5 Chunking（阶段2） |
|------|--------------------------|---------------------|
| 检索范式 | 显式溯源图建模 | 隐式块级语义匹配 |
| 匹配层级 | 词法（BM25） | 语义（E5余弦） |
| 查询处理 | 多段独立检索 → 投票聚合 | 单查询 → 多块取max |
| 模型依赖 | 无（仅 numpy） | 需 E5-base-v2 + transformers |
| 镜像大小 | ~200MB | ~2GB |
| R@10 | 0.970 | 0.983 |
| 适用场景 | 竞赛保底/快速部署 | 追求极致召回 |

**定位**：方案B（E5 Chunking）的 R@10 绝对值更高（0.983 vs 0.970），但方案A（Query Segmentation）以极低的工程成本（无模型、小镜像、CPU 可运行）实现了接近的召回水平。两方案可互补——分段 BM25 覆盖词法匹配，E5 Chunk 补足语义改写盲区。

## 六、文本对齐模块（阶段2）

### 核心方法

- E5 句子级编码 + 余弦相似度矩阵
- Jaccard 词法相似度辅助（最终权重设为 0，纯靠 cosine）
- Yukino 合并条件：位置邻近 + 语义连贯（std < 0.15）+ 最小长度 ≥ 100 chars
- K=1（仅取 Top-1 源文档对齐）

### 实验数据

| 数据集 | 样本数 | Precision | Recall | F1 |
|--------|--------|-----------|--------|-----|
| PAN26 Spot-Check | 31 | 0.496 | 0.568 | **0.530** |
| Holdout 预留集 | 500 | 0.491 | 0.531 | **0.511** |

两个独立数据集结果高度一致，F1 稳定在 0.51-0.53 区间，无小样本虚高问题。

## 七、工程经验与踩坑记录

### 1. 指标计算的隐性 Bug

**问题**：`compute_metrics()` 以 `n = len(qrels)`（全量 43,140）作为分母，而非实际测试查询数（800），导致 R@10 显示为 0.017 而非 0.920。

**修复**：
```python
n = sum(1 for qid in qrels if qid in run)  # 只计数实际评估的查询
```

**教训**：子集评估时，分子（命中数）和分母（测试查询数）必须一致。

### 2. macOS 休眠导致 `time.time()` 膨胀

**问题**：`time.time()` 在 macOS 休眠期间继续计时，导致报告的分段检索耗时高达 13,849s（实际 CPU 时间约 30 分钟）。

**缓解**：在 Linux 服务器上运行长任务时不受影响。对于 macOS，使用 `caffeinate` 命令阻止休眠。

### 3. 并行进程的隐性竞争

**问题**：两个 `seg_compare.py` 进程同时运行时，索引构建的 40K→50K 区间耗时从 72s 飙升至 525s（7x 慢）。

**原因**：两个进程共享磁盘 I/O 和内存带宽，导致倒排索引的哈希表冲突和页面换入换出。

**教训**：始终确保只有一个重负载进程在运行，使用 `ps aux | grep` 确认。

### 4. Python 输出缓冲与进程监控

**问题**：`print()` 在不加 `flush=True` 时，管道重定向到文件的输出会按 8KB 块缓冲，导致长时间看不到进度。

**修复**：所有进度输出统一使用 `print(f"...", flush=True)`。

### 5. Docker 依赖版本时效性

**问题**：`transformers==4.44.0` 在提交时已被 PyPI 下架，导致 Docker build 失败。

**修复**：简化为仅依赖 numpy，因为分段 BM25 不需要任何深度学习库。
